# Mini NPU Simulator

2차원 패턴 데이터와 필터 간의 유사도를 계산하는 **MAC(Multiply-Accumulate) 연산**을 외부 라이브러리 없이 순수 Python으로 구현한 시뮬레이터입니다.

---

## 1. 실행 방법 및 입출력 예시 (macOS 기준)

### 1.1 실행 절차
1. 터미널(또는 VS Code 내장 터미널)을 열고 프로젝트 폴더로 이동합니다.
   ```bash
   cd ~/Desktop/mini_npu
   ```
2. `main.py`와 `data.json`이 같은 디렉토리에 있는지 확인한 후 실행합니다. (Python 3.8 이상 필요)
   ```bash
   python3 main.py
   ```
3. 실행 후 원하는 모드를 선택합니다.
   - `1`: **사용자 입력 (3×3)** — 필터 A, B와 패턴을 3줄씩 공백 구분으로 입력하거나 자동 생성기로 테스트합니다.
   - `2`: **data.json 분석** — `data.json`의 `size_5`, `size_13`, `size_25` 필터와 패턴을 로드하여 일괄 판정 및 성능 분석을 수행합니다.
   - `0`: **종료** — 시뮬레이터를 종료합니다.

### 1.2 모드 1 (3×3 사용자 입력) 실행 재현 예시
- **입력 예시** (필터 A: 십자가, 필터 B: X, 입력 패턴: X):
  ```text
  필터 A:        필터 B:        패턴:
  0 1 0          1 0 1          1 0 1
  1 1 1          0 1 0          0 1 0
  0 1 0          1 0 1          1 0 1
  ```
- **출력 예시**:
  ```text
  A 점수: 1.0
  B 점수: 5.0
  연산 시간(평균/10회): 0.0010 ms (연산 횟수: 9회)
  판정: B
  ```
- **입력 검증**: 한 줄에 3개가 아닌 숫자를 입력하거나 문자가 포함되면 `"입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요. (예: 0 1 0)"` 안내와 함께 처음부터 안전하게 재입력을 유도합니다.

## 2. 구현 요약 및 설계 정책

### 2.1 핵심 모듈 구조
- **데이터 구조 (`Matrix2D`)**: $N \times N$ 크기의 2차원 리스트를 캡슐화하고 행/열 크기 일관성 검증 및 실수(`float`) 변환을 수행합니다.
- **MAC 연산 흐름 (`compute_mac_2d`)**:
  `입력(Matrix2D)` $\rightarrow$ `이중 루프 순회(r, c)` $\rightarrow$ `위치별 곱셈(p[r][c] * f[r][c])` $\rightarrow$ `누적 합산(acc += ...)` $\rightarrow$ `유사도 점수(float) 반환`
  - **점수 해석**: 두 배열의 동일 좌표 값이 모두 활성(`1.0`)일수록 곱의 합이 커지므로, **MAC 점수가 높을수록 해당 필터 패턴과 시각적 유사도가 높음**을 의미합니다.
- **방어적 키 파싱 (`parse_size_from_key`)**: `size_5_1` 같은 키에서 `_` 구분자로 차원 $N$을 추출하며, `size` 접두사 누락, 비숫자 차원(`size_abc_1`), 필터-패턴 간 행렬 크기 불일치 시 예외를 케이스 단위로 격리하여 프로그램 비정상 종료를 방지합니다.

### 2.2 라벨 정규화 및 확장 체크리스트
- **정규화 규칙 (`normalize_label`)**: `.strip().lower()` 전처리를 거쳐 `'+'`, `'cross'`, `'Cross'`, `'CROSS'` 등 대소문자·기호 혼용 표기를 **`'Cross'`**로, `'x'`, `'X'`를 **`'X'`**로 표준화합니다.
- **새 라벨(예: `'Circle'`) 확장 체크리스트**:
  1. `normalize_label()`에 동의어 매핑 추가 (`'o'`, `'circle'` $\rightarrow$ `'Circle'`)
  2. `generate_pattern()`에 해당 대칭 패턴 생성 규칙 추가
  3. `run_mode_2()`의 유효 라벨 집합(`("Cross", "X", "Circle")`) 및 필터 필수 키 검증 목록 갱신
  4. 단위 테스트 케이스 추가 및 콘솔 출력 검증

### 2.3 허용오차(`epsilon`) 및 모드별 판정 정책
- **`epsilon = 1e-9` 선정 근거 및 튜닝 가이드**: IEEE 754 배정밀도(64-bit `float`)의 기계 입실론은 약 $2.22 \times 10^{-16}$입니다. $N^2$번의 누적 덧셈 과정에서 발생하는 반올림 오차($10^{-16} \sim 10^{-14}$)를 충분히 흡수하면서도, 실제 유의미한 데이터 차이($10^{-6}$ 이상)는 놓치지 않는 안전 마진으로 `1e-9`를 채택했습니다. *(입력 스케일이 $10^6$ 이상으로 매우 크다면 `1e-6`, 정규화된 $10^{-4}$ 이하 초미세 데이터라면 `1e-12`로 조정 권장)*
- **모드별 동점 처리 정책 비교**:

| 구분 | 모드 1 (사용자 입력 3×3) | 모드 2 (`data.json` 일괄 분석) |
| :--- | :--- | :--- |
| **동점 판정 조건** | `abs(score_a - score_b) < 1e-9` | `abs(score_cross - score_x) < 1e-9` |
| **출력 레이블** | `판정 불가 (\|A-B\| < 1e-09)` (사용자 안내형) | `UNDECIDED` (표준 상태 코드) |
| **최종 집계 처리** | 단발성 결과 출력 | `expected`가 특정 클래스이므로 `FAIL`로 집계 및 사유 기록 |

## 3. 결과 리포트

### 3.1 `data.json` 실행 로그 스니펫 및 실패 원인 분석
실제 `data.json` 분석 실행 시 출력된 주요 로그입니다.
```text
--- size_5_1 ---
Cross 점수: 0.9
X 점수: 0.8999999999999999
판정: UNDECIDED | expected: X | FAIL (동점(UNDECIDED) 처리 규칙에 따라 FAIL (|Cross-X| = 1.11e-16 < 1e-09))
--- size_5_2 ---
Cross 점수: 8.9
X 점수: 0.1
판정: Cross | expected: Cross | PASS
```

총 **6개**의 테스트 케이스 실행 결과 **통과 3개(`size_5_2`, `size_13_1`, `size_25_2`)**, **실패 3개(`size_5_1`, `size_13_2`, `size_25_1`)**가 기록되었습니다. 실패 원인을 유형별로 분리해 진단한 결과는 다음과 같습니다.

1. **데이터/스키마 및 라벨 정규화 문제 (0건)**: `size_5`, `size_13`, `size_25` 필터 모두 크기·스키마 검증을 통과했으며, 이질적인 라벨(`+`, `cross`, `x`)을 `Cross`, `X`로 정규화하여 표기 차이로 인한 오탐을 0건으로 제거했습니다.
2. **로직 구현 문제 (0건)**: 명확한 패턴 차이가 있는 `size_5_2`, `size_13_1`, `size_25_2`는 100% 정확히 판정했습니다.
3. **수치 비교(부동소수점 및 동점 정책) 문제 (3건 — 의도된 FAIL)**:
   - **`size_5_1`**: `Cross = 0.9` vs `X = 0.8999999999999999` (차이: $1.11 \times 10^{-16}$)
   - **`size_13_2`**: `Cross = 7.499999999999997` vs `X = 7.5` (차이: $2.66 \times 10^{-15}$)
   - **`size_25_1`**: `Cross = 4.9` vs `X = 4.899999999999999` (차이: $1.78 \times 10^{-15}$)
   - 단순 부등호(`>`)를 사용했다면 부동소수점 잔차 오차에 의해 오판정되었을 경계 케이스들을 `epsilon = 1e-9` 정책으로 정확히 `UNDECIDED` 격리한 결과입니다.

### 3.2 시간 복잡도 분석 ($O(N^2)$) 및 벤치마크
- **측정 기준 및 주의점**: 각 크기($N$)별로 로드된 첫 번째 유효 패턴과 `Cross` 필터를 대표 벤치마크 샘플로 선택해 `time.perf_counter()`로 I/O를 제외한 순수 연산 구간을 10회 반복 평균 측정했습니다. *(참고: 파이썬 환경에서는 백그라운드 GC 동작이나 초기 루프 워밍업 여부에 따라 수 마이크로초 단위의 편차가 발생할 수 있으므로 반복 평균으로 노이즈를 완화했습니다.)*

| 크기 ($N \times N$) | 연산 횟수 ($N^2$) | $3 \times 3$ 대비 연산량 배율 | 2D 평균 시간(ms) | 1D 최적화 평균 시간(ms) |
| :--- | :---: | :---: | :---: | :---: |
| **3 × 3** | 9 | 1.00배 | 0.0010 ms | 0.0010 ms |
| **5 × 5** | 25 | 2.78배 | 0.0022 ms | 0.0014 ms |
| **13 × 13** | 169 | 18.78배 | 0.0142 ms | 0.0085 ms |
| **25 × 25** | 625 | 69.44배 | 0.0406 ms | 0.0313 ms |

- **시간 복잡도 근거 및 실행 시간 예측식**: 가로 $N$, 세로 $N$ 격자의 모든 원소 쌍을 1회씩 곱하고 누적하므로 총 연산량은 **$N^2$**이며 시간 복잡도는 **$O(N^2)$**입니다. `25×25` 실측치($t = 0.0406\text{ ms}, N^2 = 625$) 기준 단위 연산당 평균 소요 시간 계수 $k \approx 6.5 \times 10^{-5}\text{ ms}$를 도출할 수 있으며, 실행 시간은 근사적으로 **$T(N) \approx 6.5 \times 10^{-5} \times N^2\text{ (ms)}$**를 따릅니다.

### 3.3 대규모 입력($1000 \times 1000$) 처리 한계 및 우선 최적화 전략
패턴 크기가 **$1000 \times 1000$ ($N = 1,000$)**으로 커질 경우, 현재의 순수 Python 2차원 리스트 기반 직렬 구현에서는 다음과 같은 심각한 시간·메모리 병목이 발생합니다.

1. **시간 및 메모리 규모 예측 ($N = 1,000$)**:
   - **연산량 및 실행 시간**: 총 MAC 연산 횟수는 $1000^2 = \mathbf{1,000,000\text{회}}$($25\times25$ 대비 **1,600배**)로 급증하며, 예측식 $T(1000) \approx 6.5 \times 10^{-5} \times 10^6$에 따라 단일 필터 비교에만 약 **$65\text{ ms}$**, 필터 1,000개를 순차 비교하면 약 **$65\text{초}$**가 소요됩니다.
   - **메모리 사용량 폭증**: C/NumPy의 연속된 `float64` 배열은 $10^6 \times 8\text{ bytes} \approx \mathbf{8\text{ MB}}$면 충분하지만, 순수 Python의 2차원 `list[list[float]]`는 각 원소마다 24바이트 `PyFloatObject`와 8바이트 포인터를 별도 할당하므로 배열 1개당 약 **$32\text{ MB}$ 이상**(패턴+필터 쌍 기준 **$64\text{ MB}$ 이상**)의 메모리를 소모하며, 포인터 체이싱으로 인해 CPU L1/L2 캐시 미스(Cache Miss)가 급증합니다.
2. **우선순위별 최적화 방안**:
   - **1순위 — 메모리 레이아웃 평탄화 및 정적 타입 버퍼 전환 (`array` / `memoryview` / 1D 구조)**: 중첩 리스트(`list[list]`)를 제거하고 1차원 연속 메모리 버퍼로 전환하여 포인터 오버헤드(약 75% 메모리 절감)와 이중 인덱싱 비용을 제거합니다.
   - **2순위 — 캐시 블록화(Cache Blocking / Tiling) 및 스트리밍 처리**: $1000 \times 1000$ 행렬 전체를 한 번에 적재하지 않고 CPU L1 캐시 크기(보통 32~64 KB)에 맞는 작은 타일(예: $64 \times 64$ 블록) 단위로 분할 누적하거나, 제너레이터 기반 행 단위 스트리밍으로 피크 메모리 사용량을 $O(N^2)$에서 $O(N)$ 또는 $O(B^2)$로 낮춥니다.
   - **3순위 — 데이터 병렬화(Multiprocessing / SIMD) 및 NPU 하드웨어 오프로드**: 독립적인 행(Row) 또는 타일 블록을 멀티코어 CPU 워커에 분배하여 병렬 계산하고, 실제 AI 추론 환경에서는 수천 개의 MAC 연산기(PE Array)가 단일 클럭에 행렬 내적을 병렬 처리하는 NPU로 오프로드하여 직렬 CPU 대비 수십~수백 배의 지연 시간 단축을 달성합니다.
